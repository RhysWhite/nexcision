# Validation and benchmarking

NEXCISION was evaluated using a layered validation strategy designed to test correctness, failure behaviour, sensitivity to deliberately introduced faults, and computational scalability.

The complete validation materials are maintained separately in the [NEXCISION benchmarking repository](https://github.com/RhysWhite/nexcision-benchmarking) and archived at Zenodo with DOI [10.5281/zenodo.21935598](https://doi.org/10.5281/zenodo.21935598).

## Validation scope

The formal correctness and scalability experiments evaluated NEXCISION v0.1.0.

Validation was not based on successful execution of a small number of example files. It combined:

- fixed correctness and preservation cases;
- malformed-input and output-safety cases;
- genuine SPANDx matrices;
- deterministic synthetic matrices checked against an independent oracle;
- property-based testing;
- deliberate implementation faults;
- formal scalability benchmarking.

## Formal correctness validation

Experiment 1 met all predefined acceptance criteria.

### Fixed correctness and preservation cases

Seventeen permanent fixed cases tested behaviours including:

- single-site removal;
- inclusive start and end boundaries;
- positions immediately outside intervals;
- overlapping regions;
- duplicate regions;
- adjacent regions;
- reversed coordinates;
- unsorted regions;
- no-match masks;
- comments and blank lines;
- different matrix-state spacing;
- mixed-case NEXUS commands;
- inline matrix terminators.

All **17/17** cases passed.

A separate all-sites safety case also passed, confirming the explicit protection against accidental removal of every matrix row.

## Synthetic oracle validation

A deterministic corpus of **1,000 synthetic matrices** was evaluated against an independent oracle.

Results were:

| Measure | Result |
|---|---:|
| Synthetic cases | 1,000 |
| Cases passed | 1,000 |
| Coordinate-labelled site rows | 304,000 |
| Rows correctly removed | 113,740 |
| Rows correctly retained | 190,260 |
| Scenario families | 10 |
| Minimum taxa | 2 |
| Maximum taxa | 256 |
| Minimum sites | 20 |
| Maximum sites | 1,000 |

All 1,000 cases agreed with the oracle.

The synthetic validation exercised the installed wheel through the public core API rather than substituting a separate filtering implementation for the software under test.

## Genuine SPANDx matrices

Three genuine SPANDx matrices were included as real-file compatibility checks.

All **6/6** recorded checks passed.

These tests complemented the synthetic corpus by exercising NEXCISION on matrices generated by an established bacterial genomics workflow.

## Malformed-input and output-safety testing

Twenty-six cases tested malformed inputs and unsafe output conditions.

All **26/26** cases passed.

These tests exercised controlled failure behaviour rather than only successful filtering.

## Property-based validation

Property-based testing used Hypothesis 6.158.0.

Nine properties were evaluated across **1,800 configured generated examples**, together with one fixed regression case.

Results were:

- **9/9** properties passed;
- **1,800** generated examples were exercised;
- the fixed regression case passed;
- generation was deterministic;
- the Hypothesis example database was disabled for the formal run.

Property-based testing complements fixed examples by exploring many generated combinations of matrix and interval properties.

## Deliberately faulted implementations

Mutation-style validation introduced **12 deliberate implementation faults**.

The validation suite detected all **12/12** faults:

```text
mutants introduced: 12
mutants killed:     12
mutants survived:   0
mutation score:     100%
```

This demonstrates that the validation framework is capable of failing when relevant implementation behaviour is deliberately broken.

It does not prove that every possible defect has been excluded.

## Unit tests

The formal Experiment 1 record also reports **26/26** package unit tests passing.

The public repository continues to run its test suite through GitHub Actions across Python 3.10–3.14 on Ubuntu, macOS, and Windows.

## Archival revalidation

A later repository audit identified a provenance inconsistency in historical July 2026 synthetic-validation records.

Those original records contain a wheel SHA-256 checksum different from the checksum of the NEXCISION v0.1.0 wheel frozen in the benchmarking repository.

The historical records were retained unchanged rather than rewritten.

A fresh archival revalidation was therefore performed on the wheel actually frozen in the repository:

```text
NEXCISION version: 0.1.0
wheel SHA-256:
f980aa7e1f4b5ef67ebe10b4117a07af3405ee0cd3805c1d2d9e936a284689d4
```

The archival revalidation produced:

- **100/100** passing cases in the smaller synthetic suite;
- **1,000/1,000** passing cases in the full synthetic suite;
- exact oracle agreement in both suites;
- **304,000** site rows evaluated again in the 1,000-case corpus;
- a regenerated 1,000-case corpus identical to the archived corpus;
- all non-runtime result fields identical to the stored results.

Only `runtime_seconds`, an intentionally nondeterministic measurement, differed between the fresh and historical executions.

The machine-readable archival revalidation record is retained in the benchmarking repository.

## Scalability benchmarking

Experiment 2 evaluated performance under controlled conditions on one pinned logical CPU of an AMD EPYC 9374F node using node-local storage.

All **105/105** formal measured executions were correct, and all **21/21** benchmark configurations produced deterministic filtered outputs.

### Input-size scaling

Runtime increased from approximately **0.104 s** for a 0.010 GiB input to **24.24 s** for a 4.83 GiB input.

The fitted relationship was:

```text
elapsed seconds = -0.181 + 5.004 × input GiB
```

with:

```text
R² = 0.9986
```

The log-log scaling exponent across inputs of at least approximately 100 MB was **0.978**, consistent with near-linear runtime scaling under the benchmark conditions.

### Peak memory

Peak resident memory increased from approximately **0.063 GiB** to **23.42 GiB**.

The fitted relationship was:

```text
peak RSS GiB = 0.017 + 4.849 × input GiB
```

Peak memory therefore scaled at approximately **4.85 GiB RSS per GiB of input** under this benchmark format.

This is an important current implementation limitation: NEXCISION was fast at multi-gigabyte scale in the benchmark, but it was not memory-light.

### Matrix shape

Matrices of similar total byte size but different shapes showed different runtimes:

| Matrix shape | Median runtime |
|---|---:|
| Tall, many-row matrix | 5.44 s |
| Balanced matrix | 2.25 s |
| Wide, fewer-row matrix | 1.56 s |

The tall matrix was approximately **3.48-fold slower** than the wide matrix despite similar total file sizes.

The number of coordinate-labelled rows therefore contributes substantially to runtime independently of total bytes.

### Number of intervals

Increasing the exclusion list from **1** to **100,000 intervals** increased median runtime from approximately **4.41 s** to **5.00 s**.

This was an increase of **13.5%**.

Peak memory increased by approximately **0.8%**.

### Interval geometry

Disjoint, adjacent, overlapping, and nested sets of 10,000 intervals produced median runtimes spanning approximately **4.45–4.58 s**.

The total spread was **2.8%**.

No material performance penalty from overlapping or nested interval structure was observed after interval preprocessing.

### Provenance-report overhead

For an approximately 1 GiB input, enabling the deterministic JSON provenance report increased median runtime from approximately **4.43 s** to **5.48 s**.

This corresponds to an overhead of **23.6%**.

Peak memory was effectively unchanged.

## Benchmark interpretation boundary

The scalability measurements were controlled, warm-cache measurements on one exclusive Linux node using node-local XFS storage.

They should not be interpreted as:

- cold-cache performance estimates;
- network-filesystem performance estimates;
- laptop benchmarks;
- cross-platform performance guarantees.

The benchmark results describe the tested environment and workload rather than guaranteeing identical performance on other systems.
